How it fits together

You're building four long-running pieces and one app. Each phase adds one piece and proves it works before the next one depends on it.

Job taskPollerOpenSky every 30 s, weather every 10 min → JSON files in a volume
LakeflowBronze → SilverAuto Loader, clean, dedupe, feet/knots, enrich; parse METAR/TAF
Job taskDetectorEvery 15 s: holding + go-around rules → Gold + Lakebase queue
Job taskAgent workerExplains new events, forecasts next hour, scores old forecasts
Databricks AppSquawk appMap, review queue, forecast, chat, analytics
LakeflowCDF analyticsLakebase change history → agent accuracy, latency, forecast error

All the code is in the squawk folder you downloaded. Almost every decision you'll be asked about lives in one file: app/squawk_lib/config.py (names, the bounding box, stack and runway coordinates, detection thresholds). The shared code sits inside app/ because the app folder is deployed as-is and needs it too; the notebooks import it from there.

What's already been tested outside Databricks: the detection rules (10 unit tests on synthetic tracks, including one that replays the detector's sliding window), the Silver cleaning and weather parsing (on local Spark), every Lakebase table, role and query (on a real Postgres 16), the agent's tool loop, the analytics views, and the app's screens. What hasn't: anything that needs your workspace, which is what this guide walks you through.

Phase 030 mintoday

Before you start

Get your two API keys and put the code into your workspace.

  1. Create an OpenSky account and an API client

    1. Register at opensky-network.org and confirm your email.
    2. Go to your Account page → API Client and create a client.
    3. Download the credentials file. It holds a clientId and a clientSecret. Keep it somewhere private; you'll paste both values in Phase 1.

    A registered account gets 4,000 credits a day. Our box costs 1 credit per call, so polling every 30 s all day uses 2,880.

  2. Get your bootcamp LLM key

    Use the key from the DataExpert.io onboarding page, as in the Zachy homework. Note whether it's an Anthropic or an OpenAI key.

  3. Put the code in your workspace

    Recommended: push the squawk folder to a new GitHub repo, then in Databricks go to Workspace → your home folder → Create → Git folder and paste the repo URL. This also gives you something to submit, and you can commit fixes as you go.

    Quicker: in Workspace → your home folder → Import, choose the zip. Either way you should end up with /Workspace/Users/<you>/squawk containing app, notebooks, pipeline and tests.

  4. Edit app/squawk_lib/config.py

    • CATALOG: leave as squawk if you're allowed to create catalogs. If not, use a catalog you already own.
    • LLM_PROVIDER: "anthropic" or "openai", to match your key. Check the two model names under LLM_MODELS are ones your key can use.
    • Leave LAKEBASE_ENDPOINT for now; Phase 3 tells you the real value.
Phase 1Day 1third-party APIs

Start collecting data

By the end of today the poller should be running around the clock, so rows pile up while you build everything else. This is the only phase where waiting costs you days, so do it first.

Why land files first

The poller only writes raw JSON files; it never touches a table. If anything downstream breaks, the raw data is still there and the pipeline can replay it. That's also your answer to "what happens if the API goes down?": the poller retries, skips the cycle, and logs it.

  1. Run notebooks/00_setup top to bottom

    Attach it to serverless compute (or any small cluster) and run cell by cell. In section 2, the notebook adds three text boxes at the top: paste your OpenSky client ID, client secret and LLM key, run the save cell, then run the clean-up cell.

    Section 3 should print something like 214 aircraft in the box right now; credits remaining today: 3999 and a Heathrow METAR.

  2. Test the poller for five minutes

    Open notebooks/01_poller and Run all. Run by hand it stops after 5 minutes (the job sets 60). You'll see a status line every 10 cycles.

  3. Create the squawk-live job with the poller task

    1. Jobs & Pipelines → Create → Job. Name it squawk-live.
    2. First task: name poller, type Notebook, path …/squawk/notebooks/01_poller, compute Serverless.
    3. Parameters: duration_minutes = 60.
    4. Schedules & Triggers → Add trigger → Continuous. The job now restarts the moment each 60-minute run ends.
    5. Save. The first run starts on its own.

    You'll add two more tasks to this same job in Phases 3 and 4.

Check it worked

In a SQL editor or notebook, after 10 minutes or so:

sql
LIST '/Volumes/squawk/raw/landing/opensky/';

SELECT source, http_status, count(*) AS calls, min(credits_remaining) AS credits_left
FROM squawk.bronze.api_call_log
GROUP BY ALL;
  • A dated folder with a new states_*.json file every 30 s.
  • Nearly all calls 200, and credits falling by about 120 an hour.
If it goes wrong
CREATE CATALOG fails with a permissions error
Set CATALOG in config.py to a catalog you own, or ask the bootcamp admin to create squawk for you. Rerun section 1.
OpenSky token request failed: HTTP 401
The client ID or secret is wrong, or has a trailing space. Re-enter them in section 2.
Connection errors or timeouts to opensky-network.org
The workspace may block outbound internet. Ask the admin to allow opensky-network.org, auth.opensky-network.org and aviationweather.gov.
Aircraft download fails in section 4
Not a blocker. An empty table is created and Silver just won't have aircraft types.
Phase 2Day 2Spark pipelinevolume

Build the Lakeflow pipeline

Turn the landed files into clean Bronze and Silver tables with pipeline/etl.py.

What Silver does, so you can explain it

Drops rows with no position, and "stale" rows where OpenSky is repeating a position it heard more than 60 s ago. Removes duplicates of the same aircraft at the same instant (dropDuplicatesWithinWatermark, 2-minute watermark). Converts metres to feet and m/s to knots. Uses GPS altitude where available, because pressure altitude drifts by hundreds of feet with the weather. Joins aircraft type and operator. Quality rules are Lakeflow expectations, so dropped rows are counted, not silently lost.

  1. Create the pipeline

    1. Jobs & Pipelines → Create → ETL pipeline. Name it squawk-etl.
    2. Default catalog squawk, default schema bronze. (The code writes to the other schemas with full names.)
    3. Source code: add the existing file …/squawk/pipeline/etl.py. Remove any sample file the wizard created.
    4. Compute: Serverless. Pipeline mode: Triggered for now, so test runs are cheap.

  2. Add the configuration values

    In the pipeline's Settings → Configuration, add these keys. They must match config.py:

    KeyValue
    squawk.catalogsquawk
    squawk.schema.rawraw
    squawk.schema.bronzebronze
    squawk.schema.silversilver

  3. Run it once

    Click Start. The graph should show four datasets: opensky_states → positions and weather_raw → weather. Click positions and open Data quality to see how many rows each expectation dropped.

  4. Switch to Continuous

    Once a triggered run succeeds, set pipeline mode to Continuous and start it. New files now reach Silver within seconds, which the latency target depends on. You can stop it overnight if you want to save compute; the poller keeps landing files and Auto Loader catches up on the next start.

Check it worked
sql
SELECT count(*) AS rows, count(DISTINCT icao24) AS aircraft,
       max(event_ts) AS latest, count(typecode) AS enriched
FROM squawk.silver.positions;

SELECT obs_time, wind_dir_deg, wind_kt, gust_kt, visibility_sm, ceiling_ft, raw_text
FROM squawk.silver.weather WHERE kind = 'metar' ORDER BY obs_time DESC LIMIT 5;
  • latest within a minute or two of now (times are UTC).
  • Weather rows with wind and visibility filled in.
If it goes wrong
cannot import name 'pipelines' from 'pyspark'
The pipeline is on an older runtime. Change the first import to import dlt as dp; the decorators have the same names. Or set the pipeline channel to Preview.
Table or view not found: …silver.aircraft_ref
Run section 4 of 00_setup, then restart the pipeline.
Silver is empty but Bronze has rows
Check the Data quality tab. If inside_box drops everything, the bounding box in etl.py doesn't match config.py.
Phase 3Days 2–3Lakebase data modelvelocity

Detect events and queue them in Lakebase

Create the Lakebase tables, then run the detector so holding episodes and go-arounds appear in Gold and in the Lakebase queue.

Two decisions worth knowing

Deterministic IDs. The detector re-reads the last three hours every 15 s, so it sees the same holding episode hundreds of times. Each episode's ID is a hash of aircraft + type + start time, so every write is an idempotent upsert and nothing is ever duplicated.

The agent's role. 02_lakebase_setup creates a Postgres role, squawk_agent, that can only insert assessments and forecasts and change an event's status. The agent switches to it with SET ROLE, so Postgres itself refuses anything else, not just the Python code.

  1. Create a Lakebase project

    Open Lakebase (in the left sidebar, or the app switcher at the top right, depending on your workspace) → New project. Name it squawk and keep the defaults: a production branch, one read-write endpoint, scale-to-zero on.

  2. Point the config at it

    Run all in notebooks/02_lakebase_setup. The first time, it lists every Lakebase project, branch and endpoint you can see, then stops with a message asking for the endpoint. That stop is expected. Copy your project's endpoint name (projects/…/branches/…/endpoints/…) into LAKEBASE_ENDPOINT in config.py and into app/app.yaml, then Run all again.

    The notebook is safe to run all at any time: sections 4 and 5 skip themselves until Phases 5 and 6.

  3. Create the tables and the agent role

    That second run also does sections 2 and 3, which create the four tables and the squawk_agent role. The last cell in section 3 tries to write a review as the agent and should print Good - refused as expected: permission denied for table analyst_reviews. Screenshot that; it's evidence for your write-up.

  4. Run one detector cycle by hand

    Open notebooks/03_detector and run up to and including the cell marked Run ONE cycle by hand. It shows the positions it read and any episodes found.

    No episodes is normal outside busy periods. Heathrow holds most in the morning arrival peak, roughly 06:00–10:00 UK time (05:00–09:00 UTC while the UK is on summer time).

  5. Add the detector to the job

    In squawk-live, add a task detector: notebook …/notebooks/03_detector, serverless, parameter duration_minutes = 60, no dependency on the poller (they run side by side). Save; it joins the next run of the job.

Check it worked

During a busy period:

sql
SELECT event_type, location, callsign, started_at, round(duration_s / 60, 1) AS minutes,
       first_detected_at, trigger_ts
FROM squawk.gold.disruption_episodes ORDER BY started_at DESC LIMIT 20;

SELECT stack, max(holding_count) AS peak_last_hour
FROM squawk.gold.stack_occupancy_1min
WHERE minute > current_timestamp() - INTERVAL 1 HOUR GROUP BY stack;

And in Lakebase (add a new cell at the end of 02_lakebase_setup, after a Run all):

python
print(pg_df(conn, "SELECT status, event_type, count(*) FROM disruption_events GROUP BY 1, 2"))
If it goes wrong, or you get too many or too few events
Lots of holding events that look wrong
Look at a few tracks. Tighten hold_turn_deg (for example to 540) or stack_radius_nm in DETECT in config.py. Rejecting false ones in the app later gives you a detection-precision number, so some noise is useful evidence.
Holding clearly happening but nothing detected
Check that positions near the stacks are in Silver above 7,000 ft, and that the gaps between positions are under 2 minutes (the turn count ignores bigger gaps).
Go-arounds never appear
They're rare (a handful a day at most) and need good low-altitude coverage near the runways. If coverage is patchy, say so in your write-up and let holding carry the project. That was the plan B in the proposal.
password authentication failed or endpoint not found
LAKEBASE_ENDPOINT is wrong or the notebook is still using the old config. Fix it and rerun from the top (the restart cell reloads config.py).
Could not create the role
Your Lakebase role isn't allowed to create roles. The worker then writes as you and the rules are enforced only in the tool code. Carry on, and mention it in the write-up.
Phase 4Days 4–5action-taking agent

Switch on the agent

The worker explains each new event, forecasts next-hour holding and scores its old forecasts.

What the agent can and can't do

Five read tools: list_open_events, get_flight_track, get_weather, get_stack_occupancy, get_forecast_accuracy. Two write tools: save_assessment and save_forecast. The write tools validate every argument, insert with ON CONFLICT DO NOTHING (one assessment per event per model version), and only move an event from detected to assessed, so the agent can never overwrite an analyst's decision. Each run is capped at about 8 tool calls. The chat in the app only gets the read tools.

  1. Try one event by hand

    Once the detector has produced at least one event, open notebooks/04_agent_worker and run up to and including Try it on one event first. It should print the agent's one-line conclusion and Status now: assessed.

  2. Look at the trace

    Open Experiments → squawk-agent → Traces. You should see the model call each tool and then save_assessment. The trace ID is also saved on the assessment row, so the app can link an explanation back to its evidence.

  3. Add the worker to the job

    In squawk-live, add a task agent_worker: notebook …/notebooks/04_agent_worker, serverless, duration_minutes = 60, no dependencies. You now have three tasks running side by side.

Check it worked
  • Events move from detected to assessed within a minute or so (rerun the Lakebase count from Phase 3).
  • A row appears in holding_forecasts for the next hour, and gets status = 'scored' about five minutes after that hour ends.
If it goes wrong
model not found or 404 from the LLM
Change the model names in LLM_MODELS in config.py to ones your bootcamp key allows, then restart the worker.
not saved (attempt 1) in the worker output
The model replied without calling save_assessment. It retries once, then skips the event. If it happens a lot, set ASSESS_MODEL = "smart" in config.py so assessments use the stronger model (the model name saved with each assessment changes too, so your agreement numbers stay honest).
Rate-limit errors
In the job, add task parameters max_events_per_cycle = 1 and cycle_seconds = 60 to the agent_worker task.

    Find the app's service principal ID on the app's Authorization tab (a UUID). Run this with your UUID in place of the placeholder:

  5. Let the app use the Lakebase tables

    In 02_lakebase_setup, paste the same UUID into the app_client_id box at the top and Run all. Section 4 then prints Granted app access to …. The app gets read access, plus insert on reviews and update on event status, and nothing else.

  6. Open the app and review one event

    Open the app URL. On Event queue, pick an assessed event, read the agent's reasoning against the altitude chart and METARs, and save a review. Its status should change to confirmed or rejected.

Check it worked
  • Live map shows a few hundred aircraft; any that are holding show in red.
  • A review you save appears in analyst_reviews.
  • Ask Squawk answers "Which stack is busiest right now?" with numbers.
If it goes wrong

Open the app's Logs tab first. The error there nearly always names the problem.

Phase 6Day 8analytics pipeline (CDF)

Stream Lakebase changes into analytics

Turn on Lakebase Change Data Feed and build the analytics views in their own pipeline.

Why CDF fits this project

Every event moves through states: detected, then assessed by the agent, then confirmed or rejected by a person. CDF records each of those changes with a timestamp, which gives you time-to-assess, time-to-review and agent-versus-analyst agreement without adding a single line of logging to the app.

  1. Turn on CDF

    In 02_lakebase_setup, change ENABLE_CDF = False to True in section 5 and Run all. (Or use the UI: Lakebase → your project → branch → Lakebase CDF tab → Start, source schema squawk, destination squawk.lakebase_cdf.) The last cell lists each table's state.

  2. Confirm the history tables and their columns

    sql
    SHOW TABLES IN squawk.lakebase_cdf;
DESCRIBE squawk.lakebase_cdf.lb_disruption_events_history;

    You should see your columns plus _pg_change_type, _timestamp and _sort_by. If any of those three are named differently, change them in pipeline/analytics.py.

  3. Create a second, scheduled pipeline for analytics

    Keep it separate from squawk-etl, so a problem in analytics can never stop ingestion. Jobs & Pipelines → Create → ETL pipeline, name squawk-analytics, source file …/squawk/pipeline/analytics.py, serverless, mode Triggered. Add these configuration keys, run it once, then add a Schedule every 15 minutes:

    KeyValue
    squawk.catalogsquawk
    squawk.schema.goldgold
    squawk.schema.analyticsanalytics
    squawk.schema.cdflakebase_cdf
Check it worked
sql
SELECT * FROM squawk.analytics.daily_summary ORDER BY day DESC;
SELECT * FROM squawk.analytics.agent_agreement;

The app's Analytics tab now shows both tables.

If CDF won't start
An error about external or default storage
CDF needs a destination catalog backed by external storage. Ask the bootcamp admin for one, set CDF_CATALOG in section 5 of 02_lakebase_setup, and add squawk.cdf_catalog with the same value to the pipeline configuration.
A table shows as skipped
Empty tables are skipped until they get their first row. Review an event in the app, then check again.
The history tables exist but the pipeline fails
Row filters or column masks on the history tables break CDF. Don't add any.
Phase 7Days 9–10evidence

Prove it and rehearse the demo

Collect the numbers that show each requirement is met, and practise the demo at a time when something is actually happening.

  1. Volume: show you passed a million rows

    sql
    SELECT count(*) AS silver_rows, min(event_ts) AS since FROM squawk.silver.positions;
SELECT count(*) AS bronze_rows FROM squawk.bronze.opensky_states;

  2. Velocity: report the measured latency

    latency_p50_s and latency_p95_s in daily_summary are the seconds from the position that triggered a detection to the event reaching the queue. Quote the p95. If it's over 60 s, the usual cause is the pipeline running Triggered instead of Continuous.

  3. Agent quality: review at least 20 events

    Honest reviews, including disagreements, give you the agreement rate and detection precision in agent_agreement. A few disagreements make a better write-up than 100%.

  4. Rehearse the demo in the morning peak

    Plan it for roughly 06:00–10:00 UK time, when Heathrow is most likely to be holding. If it's quiet on the day, the queue still shows the last 24 hours of events, forecasts and reviews, so the demo works either way. A suggested order: map → an event with the agent's reasoning → save a review → the forecast chart → one chat question → the analytics tab.

Start, stop and defend it

Starting everything

  • Pipeline squawk-etl: Start (Continuous). squawk-analytics runs on its 15-minute schedule.
  • Job squawk-live: the continuous trigger keeps it running. If you paused it, resume it.
  • App squawk: Start, if it isn't running.

Stopping everything

Pause the job's continuous trigger, stop squawk-etl, pause the squawk-analytics schedule and stop the app. Lakebase scales to zero on its own. Once you've been graded, do this so you're not running shared bootcamp compute.

Questions you'll probably be asked

  • Why rules and not a model for detection? Every threshold can be explained and tuned, it needs no labelled data, and analyst reviews measure its precision directly.
  • Why 30-second polling? 2,880 of 4,000 daily credits, leaving room for retries, and still under the one-minute target.
  • Why GPS altitude? Pressure altitude is off by about 27 ft per hPa away from standard pressure, which is hundreds of feet on a high-pressure day.
  • How do you stop duplicate events? Deterministic IDs plus ON CONFLICT upserts and a Delta MERGE.
  • What stops the agent doing damage? Validated tool arguments, a restricted Postgres role, an update that only ever moves detected → assessed, a tool-call cap, and a read-only chat.
  • Why Lakebase and Delta both? Lakebase holds small, constantly updated operational rows the app and agent write to. Delta holds the append-heavy telemetry and the analytics. CDF connects them.
